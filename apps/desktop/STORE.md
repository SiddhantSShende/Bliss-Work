# Microsoft Store submission — BlissWork desktop

How to get BlissWork into the Microsoft Store, using the pieces already wired
up in this repo:

- `package.json` → `build.appx` — static Store packaging config (brand color,
  publisher display name, tiles).
- `build/icon.svg` + `build/gen-appx-assets.sh` — renders the brand mark into
  every required package tile size (`build/appx/*.png`).
- `build/build-appx.sh` — local/CI build wrapper.
- `.github/workflows/build-msix.yml` — manually triggered CI job that builds
  the Windows Store package on a Windows runner, verifies its manifest, and
  uploads the `.appx` as an artifact. **Use this one** — it needs no repo
  secrets and fails the build if the package doesn't match what's committed.
- `.github/workflows/store-build.yml` / `store-release.yml` — older,
  equivalent build-only workflows (no manifest verification); kept for the
  tag-triggered release flow and the optional automated Partner Center
  submission step. Safe to ignore if `build-msix.yml` covers your case.
- `build/store-assets/README.md` — the Store *listing* assets (screenshots,
  description copy) you upload by hand in Partner Center.

electron-builder packages Windows Store apps using its **`appx` target**;
there is no separate `msix` target in the installed electron-builder version.
The workflow verifies the generated AppX manifest and uploads the real
`.appx` output. Partner Center accepts `.appx` packages as well as `.msix`
packages ([Microsoft documentation](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/upload-app-packages)).

Unlike the direct-download installers in `SIGNING.md`, **you don't need to
buy a code-signing certificate for the Store** — Microsoft signs the package
itself during certification. This path is simpler than the direct-download
one for that reason.

---

## 1. Enroll + reserve the app name

1. Go to [partner.microsoft.com](https://partner.microsoft.com) and enroll
   in the developer program (one-time fee; can be waived/reduced for some
   account types — Partner Center shows current pricing).
2. **Apps and games → + Create a new app** → reserve the name "BlissWork"
   (or a close variant if taken).
3. Open the new app → **App identity**. Partner Center shows two values you
   need for everything below:
   - **Package/Identity/Name** → `STORE_IDENTITY_NAME`
   - **Package/Identity/Publisher** → `STORE_PUBLISHER_ID`
     (of the form `CN=XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX`)

**This step is already done for the current account.** The reserved values are
committed in `package.json` → `build.appx`:

```json
"identityName":         "SiddhantSShende.BlissWork",
"publisher":            "CN=8577DCDE-7A86-447A-B011-0283EB9A3FAC",
"publisherDisplayName": "SiddhantSShende"
```

so `npm run package:store` works with no environment setup. These are **public
identifiers, not secrets** — they appear in the shipped package manifest — so
committing them is fine and having them in the repo is what makes a local Store
build reproducible.

The `STORE_IDENTITY_NAME` / `STORE_PUBLISHER_ID` env vars used by
`build/build-appx.sh` are an **override** for building locally under a
different Partner Center account. The GitHub Actions workflow reads the
committed identity directly; no repository secrets are needed.

> If you re-reserve the app under a different publisher, change **both** places:
> the `build.appx` block in `package.json` *and* whichever env vars/CI secrets
> you use. A package whose identity does not exactly match the Partner Center
> reservation is rejected at submission, not at build time.

## 2. Build the .appx

### Locally (Windows or macOS only — see note below)

Using the committed identity — nothing to configure:
```bash
cd apps/desktop
npm run package:store
```

Or, to build under a **different** Partner Center account:
```bash
cd apps/desktop
export STORE_IDENTITY_NAME="OtherPublisher.BlissWork"                # from step 1
export STORE_PUBLISHER_ID="CN=XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX"  # from step 1
bash build/build-appx.sh
```
Output: `apps/desktop/release/BlissWork-*.appx`.

> electron-builder's `appx` target shells out to Windows Kits
> (`makeappx.exe`/`makepri.exe`), and only runs where Node reports
> `process.platform` as `win32` or `darwin` — **not Linux, not WSL**. If
> you're not on Windows/macOS, use CI instead (below).

### Via CI (recommended)
1. In the repository, open **Actions → Build BlissWork Microsoft Store package
   → Run workflow**.
   It builds the revision selected in GitHub Actions; it does not publish or
   submit anything to Partner Center.
2. Download `BlissWork-Store-Package` from that run's **Artifacts** section.
   It contains the `.appx` generated by electron-builder. The workflow keeps its
   real extension; it does not relabel an AppX file as `.msix`.

The workflow uses the public identity and publisher already configured in
`apps/desktop/package.json`; no signing or Store API secrets are required to
build the artifact. Microsoft signs Store-distributed packages as part of its
certification and distribution process. The workflow artifact is not a
standalone signed, trusted installer.

## 3. Re-render brand assets (only if the logo changes)
```bash
cd apps/desktop
bash build/gen-appx-assets.sh   # requires rsvg-convert: sudo apt install librsvg2-bin
```
This regenerates `build/icon.png` and all of `build/appx/*.png` from
`build/icon.svg` (the same mark used on the website favicon). The PNGs are
committed so CI doesn't need `rsvg-convert` installed.

## 4. Prepare the Store listing
Follow `build/store-assets/README.md` to capture screenshots (Microsoft
requires at least one, 1366×768 or 1920×1080 — real UI, not mockups) and
pull together the description copy.

In Partner Center, fill in:
- **Properties**: category **Productivity**, support contact info.
- **Age ratings**: complete the ratings questionnaire (BlissWork should
  qualify for the lowest/no-rating tier).
- **Pricing and availability**: Free, pick your markets.
- **Store listings**: screenshots, short/full description
  (`build/store-assets/README.md` has starter copy).
- **Packages**: upload the `.appx` from step 2.

## 5. Submit for certification
**Submit for certification** in Partner Center. Microsoft's automated +
manual review usually takes 24–72 hours. Common rejection reasons to check
before submitting:
- App crashes on first launch on a clean Windows VM.
- Missing/broken privacy policy URL (BlissWork has one at
  `https://blisswork.rnrtechs.com/privacy`; verify it remains available and
  that the Store listing links to this exact page).
- Windows desktop activity disclosure: while signed in, the app records the
  foreground executable name and active/OS-idle spans (see
  `apps/desktop/src/main/activity-agent.ts`). **`BlissWork-Privacy-Policy.txt`
  does not describe this behavior yet** — add a plain-language disclosure of
  it (and update the hosted `/privacy` page to match) before submitting, or
  certification can reject the listing for an undisclosed data practice.
- Placeholder-looking branding — already fixed here (the icon used to be
  electron-vite's default sample icon; `build/icon.svg` is now the real
  BlissWork mark).
- **Deep links must be declared in the package manifest.** A Store app cannot
  register a URI scheme at runtime the way a desktop installer can, so
  `app.setAsDefaultProtocolClient("taskboard")` alone is not enough — Windows
  only routes `taskboard://` to a Store app if the package declares it. The
  `protocols` key in `package.json` generates that declaration
  (`<uap:Extension Category="windows.protocol">`) for AppX, and the equivalent
  for macOS (`CFBundleURLTypes`) and Linux (`MimeType=x-scheme-handler/…`).
  Verify it survived packaging before submitting:
  ```bash
  # unzip the .appx and grep the manifest
  unzip -p release/BlissWork-*.appx AppxManifest.xml | grep -A3 windows.protocol
  ```
  Without it, emailed invite links and the OAuth return silently do nothing for
  every Store user.

## 6. After approval
- The Store handles updates: bump `version` in `package.json`, rebuild
  (steps 1–2 don't need repeating unless identity changes), and submit a new
  package as an update in Partner Center.
- Consider wiring `electronUpdaterAware: true` under `build.appx` later if
  you want in-app update checks to recognize Store-installed copies
  differently from direct-download ones — not set up here since this repo's
  direct-download builds already use their own updater path (see
  `SIGNING.md`).

## Submission and updates

The workflow only builds and uploads an artifact. Upload the `.appx` to Partner
Center manually, complete certification, and submit it there. Store-installed
builds are updated by the Store; the existing `electron-updater` feed is for
direct download installers and does not install Store packages.
