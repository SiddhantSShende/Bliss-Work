# BlissWork Activity — Safari Web Extension wrapper

A macOS Xcode project wrapping `apps/extension`'s bundled output as a Safari
Web Extension, in the same structural shape Apple's own
`safari-web-extension-converter` produces:

- **`BlissWork Activity`** — the container app (SwiftUI). Ships no
  activity-tracking logic; its only job is to exist as an installable app
  Safari can enable the extension through, and to point the person at
  Safari's own extension settings.
- **`BlissWork Activity Extension`** — the Safari Web Extension app-extension
  target. `Resources/` is a **copy** of `apps/extension/dist-safari/`'s
  output (`npm run build:safari -w @taskboard/extension`) — the exact same
  `background.js`/`manifest.json`/`options.html` every other browser target
  loads, built from the exact same `tracker.ts`/`background.ts`/
  `siteEnrichment.ts` source. Nothing Safari-specific exists in that
  TypeScript; the only Safari-specific code in this whole feature is
  `SafariWebExtensionHandler.swift`, which this extension never actually
  uses (see its own doc comment) but which the `NSExtension` point requires.

## Keeping `Resources/` in sync

This is a **copy**, not a symlink or a build-time reference, so the Xcode
project stays self-contained for someone who opens it without having run
the TypeScript build first. After changing anything under `apps/extension/src`,
regenerate it:

```sh
cd apps/extension
npm run build:safari
rm -rf "xcode/BlissWork Activity/BlissWork Activity Extension/Resources"
cp -r dist-safari "xcode/BlissWork Activity/BlissWork Activity Extension/Resources"
rm -rf dist-safari
```

## What is, and is not, done here

**Done, as real source you can open in Xcode:**
- The two-target project structure (`project.pbxproj`), hand-authored to the
  same shape the real converter emits — never opened in Xcode itself (this
  environment has none), so its structural correctness was checked
  mechanically (brace/paren balance, every object-id cross-reference
  resolves, every referenced file path exists on disk) but **not** by an
  actual Xcode project load.
- `Info.plist` / entitlements for both targets, including the
  `com.apple.security.network.client` entitlement on the **extension**
  target (not the container app — App Sandbox entitlements are per-target,
  and the extension is the process that actually calls `fetch()`).
- A minimal SwiftUI container app that opens Safari's own
  extension-preferences pane via `SFSafariApplication`.
- The boilerplate `SafariWebExtensionHandler` every converter output
  includes, documented as unused (this extension has no native-messaging
  calls to handle — see its own comment).

**NOT done here, and cannot be done without a real Mac + Xcode + an Apple
Developer Program membership for signing:**
- Actually opening this project in Xcode and confirming it builds.
- Running `safari-web-extension-converter` itself (this project was
  hand-authored to its expected output shape rather than generated by it —
  running the real tool against `dist/` and diffing against this project
  would be the strongest confirmation, and has not been done).
- Code signing (ad-hoc or Developer ID) and notarization.
- Loading the built app in a real Safari and confirming:
  - the extension appears and can be enabled at all,
  - `chrome.tabs`/`chrome.storage.session`/`chrome.alarms`/`chrome.idle`
    behave the way this extension's `background.ts` assumes (Safari's
    WebExtension API coverage has historically had gaps and behavioral
    differences from Chromium/Firefox — see `../docs/BROWSERS.md`),
  - the `com.apple.security.network.client` entitlement actually permits
    `fetch()` to `POST /telemetry/ingest/agent` under App Sandbox in
    practice,
  - `host_permissions: []` really does mean no per-site permission prompt
    under Safari's own permission UI (which is not identical to Chrome's).
- Actual app icons (`Assets.xcassets/AppIcon.appiconset` has the required
  `Contents.json` slot declarations but no PNG files — `apps/extension/icons/
  icon128.png` exists and can be scaled to the required sizes, but generating
  binary image assets is outside what should be fabricated sight-unseen).
- A real Apple Developer Team ID and bundle identifier if `com.blisswork.
  activity`/`com.blisswork.activity.extension` are not what BlissWork
  actually wants to register — these are placeholders in the same spirit as
  `manifest.firefox.json`'s gecko id, and are a decision only the org can make.

See `../docs/BROWSERS.md` §6 for the full picture of what "Safari support"
still requires before it can honestly be called shipped.
