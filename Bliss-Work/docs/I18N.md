# UI localization

BlissWork's UI is translated from **static catalogs shipped in the build** — no
runtime translation service, no credentials, no network at language-switch time
beyond one cached JS chunk. Web and the Electron renderer run the same code from
`packages/app/src/i18n/`.

Languages: `en` (source and fallback), `es`, `fr`, `de`, `hi`, `pt` (Brazilian),
`ja`, `zh` (Simplified), `ko` — the eight non-English ones are gated until reviewed
(see "Release gate"). The list lives in **one place**:
`packages/app/src/i18n/locales.ts`.

## How it fits together

| Piece | File |
|---|---|
| Language registry (codes, native names, `ready` flag) | `i18n/locales.ts` |
| Pure helpers: precedence, persistence, init options | `i18n/core.ts` (React-free; Electron main imports it) |
| English bundled eagerly; other locales lazy, one hashed chunk per namespace | `i18n/catalogs.ts` |
| i18next + react-i18next init | `i18n/index.ts` |
| Active language, switching, `<html lang/dir>`, desktop sync | `i18n/LanguageProvider.tsx` |
| Selector (native names) | `i18n/LanguageSwitcher.tsx` |
| Electron secondary windows follow the main window | `i18n/windowLocale.ts` |
| Electron main process (menu, tray, OS notifications, dialogs) | `apps/desktop/src/main/i18n.ts` + `desktop` namespace |
| Words `@taskboard/ui` renders itself | `packages/ui/src/strings.tsx`, fed by `i18n/UiStringsBridge.tsx` |
| Locale-aware number/duration formatting | `i18n/format.ts` |
| Catalogs | `i18n/locales/<code>/<namespace>.json` (namespace = feature) |
| CI parity check | `scripts/check-locales.mjs` (`npm run i18n:check`) |

**Language precedence:** persisted choice (`localStorage["tb-locale"]`) → system
language (`navigator.languages`) → English. Only an explicit pick is persisted.
Regional tags map to the base language (`pt-BR` → `pt`); Traditional Chinese
(`zh-TW`, `zh-Hant`, …) is deliberately *not* mapped to the Simplified catalog.

**Failure behaviour:** a missing key, namespace or locale falls back to English.
If a locale's chunk cannot load (offline, CDN error) the app stays in English; a
failed *boot* keeps the stored choice so the next launch retries, a failed
*user switch* shows `common:language.switchFailed` and changes nothing. English is
bundled, so the UI is never blank. In the Electron build every chunk is inside the
asar, so switching works fully offline.

## Adding or changing text (developers)

1. Edit **only** `locales/en/<namespace>.json`. Keys are `camelCase`, grouped
   `area.element`; one key per sentence — never build sentences from fragments.
2. Use it: `const { t } = useTranslation("tasks"); t("area.element", { name })`.
   Outside React: `import i18n from "../i18n"; i18n.t("ns:key")` — resolve at call
   time, never in a module-level constant (it would freeze English).
3. **Plurals:** give `key_one` / `key_other` and pass `count`. Never
   `count === 1 ? … : …` or `+ "s"`.
4. **Interpolation:** `{{name}}`. Inline markup via `<Trans>` with numbered/named
   components; no HTML in values.
5. **Dates / numbers / durations / lists:** `Intl.*` with `i18n.language`
   (see `i18n/format.ts`), never a hardcoded locale (`"en-US"`).
6. Do not compare against translated text (`label === "Today"`); compare the
   underlying value.
7. `npm run i18n:check` — it will now fail for every other locale until they are
   translated (see below). Commit the English change with the translations.

Text that is **stored or sent** (message bodies, meeting titles, server-written
system messages, notification text, emails, API error messages) is not part of UI
localization — it is generated in one language and displayed as-is. See
"Not covered".

## Adding / reviewing translations

Each non-English locale mirrors English exactly: same files, same keys, same
order. `node scripts/check-locales.mjs [locale…]` fails on a missing/extra file or
key, an empty value, a different set of `{{placeholders}}`, markup tags or URLs,
and on plural categories that do not match the language's CLDR categories
(`ja/zh/ko`: `_other` only; `de/hi/en`: `_one`,`_other`; `es/fr/pt`: `_one`,`_many`,
`_other`). `--warn` also lists values identical to English.

Per locale, `locales/<code>/GLOSSARY.md` records the term choices (Task, Channel,
Meeting …). Keep the same English phrase translated the same way everywhere, and
keep the brand and third-party product names untranslated.

**Release gate:** `ready` in `locales.ts` controls whether a language is offered
to users. **All eight non-English catalogs are `ready: false`**: they were
authored without a native-speaker review, so production builds show English only and
ignore any stored/system language they cannot offer. The catalogs are still
validated by `check-locales` and loaded by tests. Development builds
(`import.meta.env.DEV` — `npm run web`, `npm run desktop`) preview **every** locale
so reviewers can use them; each locale's `GLOSSARY.md` lists the term choices to
check. To release a language, have a fluent speaker review it, then flip that one
flag to `true` in the same PR that records the sign-off. `check-locales` prints which
locales are still gated.

## Layout checks

German/French/Hindi are the longest. When touching dense UI (toolbars, chips,
cards), switch to `de` and `hi` and look. CJK needs no extra width but check line
height.

## Not covered (separate work)

* **Server-authored text** shown verbatim: channel system messages
  (`messaging-svc/internal/store/*`), notification titles/bodies
  (`notification-svc/internal/consumer`), emails (`email-worker/app/templates.py`),
  API error messages. The notification panel and desktop notifier also *parse* the
  English delimiters (`": "`, `" in #"`), so localizing those strings in place
  would break them — the fix is structured payloads (`kind` + params, stable error
  codes) rendered with client templates.
* Mobile (`apps/mobile`) has no i18n yet; `i18n/core.ts` and `locales.ts` are
  React-free so it can reuse them.
* Right-to-left languages: `dir` is wired from the registry, but the layout has not
  been audited for logical properties.
* A per-user server-side language preference (would follow `0021_theme_prefs.sql`).
