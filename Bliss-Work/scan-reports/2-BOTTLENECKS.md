# BlissWork scan — Report 2 of 3: PERFORMANCE BOTTLENECKS

Scan date 2026-10-06 · scope `Bliss-Work/`. Same method and caveats as Report 1 (TS findings are code-reading; nothing was load-tested; the live-host findings in the last section were measured directly).
Severity: **High** = hits most users/ops now · **Med** = degrades under realistic load or data growth · **Low** = minor/rare.
"Bottleneck" here = something that will be slow, starve a resource, or grow without bound. Pure tidy-ups are in Report 3.

## Go services

### notification-svc
- **P-NOT-1 [Med] Per-recipient write = 3 sequential round trips; a channel message costs 3N in one tx** — `internal/consumer/consumer.go:512-531,544-562,591-608`, `create()` at `:752/:767/:798`. INSERT consumed_events + notifications + outbox per member plus an Info log each; 20 000 members ≈ 60 k statements per Kafka message. **Fix:** one `INSERT … SELECT unnest()` per table (or `pgx.Batch`); drop per-row log.
- **P-NOT-2 [Med] Outbox publisher capped at 100 rows / 500 ms and holds a DB tx across the Kafka write** — `internal/outbox/outbox.go:73-86,122-128,209`. ≈200 events/s per replica, sleeps even with backlog; 500-member message takes ~2.5 s to publish; claim tx + one of 10 pool conns held during a RequireAll write; with SKIP LOCKED two replicas break per-key order. **Fix:** loop while batch full, bigger LIMIT, `ORDER BY (created_at,id)`, single publisher if order matters.
- **P-NOT-3 [Med] Unread-count/list queries lack a supporting index; notifications never pruned** — `internal/httpapi/httpapi.go:351,167-173`, `migrations/001_init.sql:14` (only `(recipient_id, created_at DESC)`), `cmd/prune-event-tables/main.go:90-110` (prunes outbox + consumed_events only). Badge counts all rows per recipient; index lacks `id`. **Fix:** indexes `(recipient_id, created_at DESC, id DESC)` and partial `(recipient_id) WHERE read_at IS NULL`; add retention for `notifications`.

### ws-gateway
- **P-WS-1 [Med] Default broadcast fan-out writes replay outbox one recipient at a time on the single Kafka loop** — `internal/fanout/fanout.go:174-203`, `store/outbox.go:60-69`, default mode `config/config.go:163`. 5 000-member channel = 5 000 sequential RTTs (+ retry sleeps) → live delivery lags node-wide. `AppendOutboxMulti` exists but only the routed path uses it. **Fix:** one `AppendOutboxMulti` per event, retried as a unit.
- **P-WS-2 [Med] Routed push sends one payload copy per recipient and never chunks** — `internal/router/router.go:196-216`, `push/push.go:50` (8 MiB cap), `server/push.go:49`. 8 KiB × 1 000 recipients hits the cap → node answers 400 and the whole node batch is lost live. **Fix:** one `Broadcast{UserIDs,Payload}` per node, chunk the user list.
- **P-WS-3 [Med] Presence is O(org size) per event; `/presence` has no throttle** — `server/server.go:179-196`, `store/presence.go:216-228`, `server/conn.go:566`, `presence/presence.go:111-143`. Each hello/poll = ZREMRANGEBYSCORE (write) + ZRANGE whole org set; each transition re-reads it and pushes an N-user list → O(n²) on a hot key during deploy/Redis blip; cleanup under 3 s timeout can lose offline events in big orgs. **Fix:** move clients to `/presence/query`, reap on timer, debounce, rate-limit.
- **P-WS-4 [Med] `channel.message.created` stored in full once per member in Redis** — `contract/compact.go:39-52` (only `message.created` compacted), `fanout/fanout.go:172`, `router/router.go:104`. 20 k-member channel × 8 KiB ≈ 160 MB into the 2 GiB `noeviction` Redis. **Fix:** compact refs for channel messages / store payload once.

### messaging-svc
- **P-MSG-1 [Med] `ListChannels` / `ListConversations` / `UnreadCounts` unbounded correlated counts** — `store/channels_read.go:104-215`, `store/conversations.go:271-330`, `store/unread_counts.go:35-77`. Counts CTE reads all members of every channel the user is in + per-channel unread `count(*)`; user in 50 channels × 10 k members reads ~500 k member rows per call; no pagination; runs on primary pool (MaxConns=10) though a replica is configured. **Fix:** cap counts ("99+"), keep `member_count` as a counter, use replica.
- **P-MSG-2 [Med] Every channel message re-reads the member list and embeds up to 20 000 ids (~780 KB) in the event** — `store/channels.go:752-785` (`ORDER BY joined_at LIMIT 20001`), `store/append_channel.go:107,181`, `migrations/0002_channels.sql` (no `(channel_id, joined_at)` index). Sort + ~780 KB jsonb outbox row per send; channels >20 k silently stop reaching later joiners. **Fix:** don't embed rosters (use `/internal/channels/{id}/members`) or cache + index.
- **P-MSG-3 [Med] Per-IP rate buckets too small** — `middleware/ratelimit.go:45-49`, `api/api.go:49,198,230-234`. `/api/v1` 300 req/min per IP before auth (office NAT hits 429s); all `/internal/*` callers share one 100 req/s bucket per source IP — one ws-gateway pod doing an ack POST per active recipient per 500 ms exceeds it at ~200 concurrent chatters; 429s trip the ack breaker. **Fix:** configurable limits; token-auth internal callers; key by user after auth.
- **P-MSG-4 [Med] Outbox poller holds a DB tx (1 of 10 conns) across a RequireAll Kafka write; no ordering tiebreak** — `internal/kafka/outbox.go:25,56-70`, `store/outbox.go:250-360` (`ORDER BY created_at` at :288). Slow Kafka starves requests; rows of one tx share `created_at`; replicas break per-key order. **Fix:** short claim tx (UPDATE…RETURNING), publish outside, `ORDER BY (created_at,id)`, loop while full.

## auth-svc
- **P-AUTH-1 [High] Avatar data-URI (≤500 KB) decrypted and shipped in every user DTO** — `app/service.py:133` (`user_dto`), `:256` (`_user_dtos_from_rows`), `routes/auth.py:715-760` (`MAX_DIRECTORY_PAGE=5000`), `routes/members_service.py:144`, `schemas.py:15`. Every login, refresh (~5 min/client), `/auth/me`, directory, member list AES-decrypts the avatar synchronously on the event loop and inlines it; a 5 000-member directory = hundreds of MB. **Fix:** cacheable avatar endpoint / small thumbnail; drop `avatar_enc` from session/refresh/directory payloads.
- **P-AUTH-2 [Med] Outbox poller sends one message at a time inside the claim tx** — `app/events/poller.py:200` (same in `task-svc/app/outbox.py`, `sticky-svc/app/outbox.py`). `send_and_wait` per row (≤100) with FOR UPDATE + pool conn held; slow broker (40 s default timeout) pins a connection. **Fix:** `send()` all, await futures together, then mark published.
- **P-AUTH-3 [Med] Argon2 hash/verify runs while a DB tx and row locks are held** — `routes/auth.py:255`, `service.py:1054,1095`, `routes/account_service.py:209` (under FOR UPDATE on token), `routes/mfa_service.py:316`. ~50–150 ms each pins a pooled conn (pool 5+5/replica). **Fix:** verify in a short first tx / released conn, then write tx.
- **P-AUTH-4 [Med] N+1 role lookups per membership** — `service.py:912` (`memberships_for_identity`), `:932`, `routes/members_service.py` (`leave_org_tx`). `roles_for_user` per org although `roles_by_user_id` batches. **Fix:** use the batch.
- **P-AUTH-5 [Low] `list_active_sessions` aggregates the whole refresh-token history** — `service.py:710`. ~288 rotation rows/day per active client kept 30 days, GROUP BY on each Sessions/admin view. **Fix:** prune rotated/revoked after replay-grace; or per-family table.
- **P-AUTH-6 [Low] Audit chain: 3 round trips under per-org advisory lock, attacker-writable** — `service.py:1186` (`write_audit`), `routes/session_events.py:201`. Serialises an org's auth traffic; unauthenticated failed logins add permanent rows (8 per lockout cycle). **Fix:** single INSERT…SELECT; sample/aggregate `login_failed`.
- **P-AUTH-7 [Low] `verify_audit_chain` loads the entire org audit log** — `service.py:1237`, `routes/internal.py:55`. **Fix:** server-side cursor chunks.
- **P-AUTH-8 [Low] CAPTCHA render CPU-bound on the event loop; in-process store never swept** — `routes/captcha.py:24`, `captcha_image.py:274` (pure-Python pixel loop, six `ImageFont.load_default` per image), `captcha_service.py:98`. Unauthenticated; without Redis `_local` entries expire only on read (flood leaks memory). **Fix:** `to_thread`, cache font, evict on put.
- **P-AUTH-9 [Low] Unbounded list endpoints** — `routes/invites.py:73`, `routes/members_service.py:144` (limit optional) — includes decrypted avatars. **Fix:** default limit + keyset.
- **P-AUTH-10 [Med] i18n catalog: no single-flight, sequential per-namespace, failures not negative-cached** — `routes/i18n_service.py:345` (local fallback cache `:200` unbounded, ignores TTL). Cold/Google-failing locale: each concurrent user repeats Google calls (quota/cost amplification); outage = up to namespaces × 8 s per request. **Fix:** single-flight per locale, parallel namespaces, brief failure cache, bound dict.

## task-svc
- **P-TASK-1 [Med] Network calls to messaging-svc run inside the schedule claim tx** — `app/schedule_worker.py:183` (`_claim_due_schedule`), `:144` (`_resolve_targets`), pool `db.py:25`. Row FOR UPDATE + 1 of 5+5 conns held across ≤20 sequential HTTP calls (2–5 s timeouts), retried each tick; starves requests and other loops. **Fix:** resolve before claiming, or claim→commit→resolve→materialise with version check.
- **P-TASK-2 [Med] `/tasks/sent`: serial decrypt on loop, no matching index, fan-out per page** — `routes/tasks_read.py:241`, `migrations/001_init.sql:35` (only `(org_id, sender_id)`). Sorts all sender's tasks with OFFSET paging; tasks × assignees (100×500) each awaited-decrypted while session open (unlike `_sticky_list`). **Fix:** index `(org_id, sender_id, created_at DESC, id DESC)`; `warm_dek_versions` + `decrypt_batch_cached` off-loop.
- **P-TASK-3 [Med] Inbox rows embed full participants `json_agg`** — `routes/tasks_read.py:63`. ≤100 tasks × ≤500 assignees = up to 50 k objects per page. **Fix:** cap/count + first N; fetch rest on demand.
- **P-TASK-4 [Med] Export: OR scope defeats the index; serial decrypt** — `routes/tasks_export.py:66-68,115`. `(t.sender_id = :me OR ta.assignee_id = :me)` scans org assignments; ≤5000 rows × ≤3 awaited decrypts holding a conn. **Fix:** two `UNION ALL` index scans + batch decrypt.
- **P-TASK-5 [Med] `add_participants`: per-user INSERT + outbox loop; quadratic event payload** — `routes/participants.py:148`. ≤500×2 statements in one tx; every event embeds `members=[sender,*member_ids,*add_ids]` → N² (hundreds of KB–MB per call). `create_task` already batches. **Fix:** multi-row insert; send members once/not at all.
- **P-TASK-6 [Low] New httpx client and serial calls per channel** — `routes/tasks_write.py:30` (`_resolve_channel_members`). **Fix:** shared `AsyncClient` + `gather`.

## sticky-svc
- **P-STK-1 [Low] Consumer subscribes to all of `auth.events`** — `app/consumer.py` (AUTH_TOPIC). Needs only `org.deleted`; every login/session event fetched and JSON-parsed. **Fix:** filtered topic.

## email-worker
- **P-EW-1 [Med] `email_consumed` / `mail_transport` have no retention** — `migrations/0001_init.sql`, `0002_mail_transport.sql`; only DELETEs are for 'pending' (`relay_consumer.py:924,1300`). Every relayable event inserts a row (even online recipients); random-uuid PK index grows forever. **Fix:** nightly prune of 'sent' older than Kafka retention + margin.
- **P-EW-2 [Low] Sequential batch under SMTP trouble can exceed `max_poll_interval_ms`** — `app/worker.py:155-171`, `relay_consumer.py:277-295`. Up to 100 msgs × ~108 s worst case > default 300 s → consumer evicted, commit fails, rebalance. **Fix:** lower `max_records` / raise interval.

## integrations-svc
- **P-INT-1 [Med] OAuth callback holds a pooled DB conn + open tx across provider calls** — `routes/oauth.py:123-166`. `DELETE oauth_states` then `exchange_code` + `fetch_identity` (3 attempts × 10 s) with the connection held; pool 5+5 → ~10 slow callbacks starve every route and the refresh worker. **Fix:** commit/decrypt, release, HTTP, new session to store.
- **P-INT-2 [Low] `provider_activity` / send-attempt tables never pruned; hub query can't use its index** — `jobs/prune_event_tables.py:61-95`, `routes/integrations.py:106-112` (`owner_user_id = :uid OR IS NULL ORDER BY occurred_at DESC LIMIT 100`), `migrations/0001,0013,0015`. **Fix:** retention targets; `UNION ALL` of two index-ordered branches.

## telemetry-svc
- **P-TEL-1 [Med] "Batched" ingest still does one INSERT round trip per row** — `app/ingest.py:166-182` (loop at 179-180). Consumer batches of 200 and beacons of 100 = N sequential RTTs in tx; docstring claims multi-row insert. **Fix:** `INSERT … SELECT unnest(...)` / Core multi-values.
- **P-TEL-2 [Med] Nightly rollup defeats partition pruning** — `app/jobs/rollup.py:116-119` (`(occurred_at AT TIME ZONE tz)::date = :day`). Scans all 90+ daily partitions per rolled-up day (whole table in backfill). **Fix:** range on `occurred_at` via `day_bounds`.
- **P-TEL-3 [Med] Roster's last-login query scans org's whole 7-day event stream** — `routes/timeline.py:289-320` (comment at 293 is wrong). No index on category/action. **Fix:** partial index `(org_id, occurred_at DESC) WHERE category='auth'` or use `user_sessions`.
- **P-TEL-4 [Low] Prune holds ACCESS EXCLUSIVE on parent for whole tx; deletes unindexed** — `jobs/prune.py:187-194,205-247`. `DROP TABLE` partition locks `activity_events` until final commit, no `lock_timeout` — a DROP queued behind a long ingest tx blocks all inserts; `user_sessions`/`activity_sessions` `ended_at < …` deletes seq-scan. **Fix:** commit per drop with `lock_timeout`; `(ended_at)` indexes.

## Web frontend
- **P-WEB-1 [High] livekit-client (544 KB chunk) on critical path of every `/app` route** — `packages/app/src/lib/useCall.tsx:7` (`import { isGetUserMediaDenied } from "./useCallRoom"`); dist `useCall-*.js` → `useCallRoom-*.js`; `AppShell-*.js` imports `useCall`. `vite.config.ts` claims livekit is behind dynamic imports and `CallRoomLazy` defers it, but this import defeats it. **Fix:** move helper to a livekit-free module.
- **P-WEB-2 [Med] emoji-picker-react (310 KB) statically bundled into chat views** — `features/EmojiPicker.tsx:1`; consumers `Composer.tsx:6`, `MessageActions.tsx:21`, `CallChat.tsx:25`. Opening any DM/channel downloads it. **Fix:** `React.lazy` boundary.
- **P-WEB-3 [Med] Route chunks not requested until session refresh finishes** — `packages/app/src/App.tsx:421-465,233-345`. index.js → `/auth/refresh` (≤30 s) → AppShell chunk; logged-out visitors wait too. **Fix:** prefetch AppShell/Login at load; public routes outside gate.
- **P-WEB-4 [Med] Chat thread: no virtualization/memoization, framer-motion per bubble** — `features/ChatThread.tsx:~470-700`; no `React.memo` in packages/app. Every render re-runs `groupMessages`, `renderBody`, `parseChatEnvelope`, `linkifyMessage`, `new Intl.Segmenter` per message (`:80-85`); prepend re-animates all rows; list unbounded. **Fix:** memo rows/groups, hoist Segmenter, virtualise/cap.
- **P-WEB-5 [Med] Signed attachment URLs for the whole thread re-minted when one appears** — `lib/useAttachmentLinks.ts:24-46`, `features/useChatMedia.tsx:515-540`. Query key = all ids joined → N/50 requests per new media message and every 8 min; changing token changes every `src`. **Fix:** per-id cache, refresh near expiry.
- **P-WEB-6 [Med] Invalidating paged inbox refetches every loaded page sequentially** — `lib/useCursorPagination.ts:21-110` (no `maxPages`), invalidated from `queryBridge.tsx` and `routes/MailList.tsx:166-182`; each action also invalidates ~8 other keys. **Fix:** `maxPages`; patch cache on known results.

## Host / runtime (measured live on this machine, 2026-10-06)
- **P-HOST-1 [High] Unbounded Docker json-file logs — 4.4 GB** — `/var/snap/docker/common/var-lib-docker/containers` = 4.4 GB; no `logging:` in `docker-compose*.yml` (0 occurrences) and `/var/snap/docker/current/config/daemon.json` sets only `log-level`. Largest: integrations-svc dev 876 MB, prod integrations-svc-1/-2 766 MB each, prod cadvisor 404 MB, telemetry-svc dev 254 MB, prod postgres 216 MB. Root fs 72 % (56 GB free). **Fix:** `logging: {driver: json-file, options: {max-size: 50m, max-file: "3"}}` via a compose `x-logging` anchor, or daemon.json; recreate containers (existing logs don't shrink until then).
- **P-HOST-2 [Med] Log amplification** — B-REPO-2 (outbox "connected" line every 0.5 s) is the main source of the integrations-svc volume; uvicorn access logs of `GET /metrics` and `/readyz` (hundreds per few minutes) are the next. **Fix:** log-on-create; filter access log for health/metrics paths.
- **P-HOST-3 [Low] Prod Kafka at 77 % of its memory limit** — `docker stats`: `task-board-prod-kafka-1` 1.161 GiB / 1.5 GiB (limit 1 610 612 736 B, OOMKilled false, 0 restarts). Little headroom for a burst or the 7-day outbox backlog; an OOM-kill would stall every consumer. **Fix:** raise limit / cap heap, alert on `container_memory_working_set_bytes` ratio.
- **P-HOST-4 [Low] Dev and prod stacks share one 23 GB host** — 40+ containers incl. both `task-board-*` (dev) and `task-board-prod-*` (prod), two Kafkas (1.16 GiB each), two Postgres; dev telemetry-svc was observed at ~31 % CPU in a one-shot `docker stats` sample (idle in a later `docker top`). Also see memory note: dev and prod LiveKit collide on 7880. **Fix:** stop the dev stack when not in use.
